# ISO 25010 selected improvements — local implementation

Implemented the approved navigation, College Setup validation, and existing assessment save/resume repairs. No commit, push, deployment, migration, dependency, environment-file, credential, or hosting-configuration change was made.

## Behavior

- College Dashboard displays **View Assessment Summary** only when the authenticated `/api/recommendations/latest` response includes a saved recommendation header linked to an assessment and at least one accessible recommendation. Missing, incomplete, or unavailable results leave the option hidden without blocking tracking.
- Summary uses the existing saved-result endpoint rather than the generating `/api/results` endpoint. Its existing View Full Results button opens the same Results page with `?saved=1`, which also reads saved results only. These paths do not generate recommendations or refresh explanation wording. Normal post-assessment recommendation generation remains available through the original `/results` flow.
- Summary returns active College tracking users to `/college`; users without active tracking retain `/college/setup`. Saved Results retains access to Summary alongside its College return action. Existing routes and responsive styling are reused.
- Results return navigation follows its entry context: Summary opens saved results with `returnTo=summary`, and **Return to Summary Dashboard** takes precedence over active College status. Older `?saved=1` Summary links retain the same behavior, including after refresh. Unqualified post-assessment Results keeps the existing College return for active tracking users. The College informational note depends on actual tracking status independently of the return destination. No arbitrary return URL is accepted.
- Career Path follows the same entry-source rule: the Summary chooser shows **Back to Summary Dashboard**, while Results-origin details show **Back to Results**, regardless of College status. A course opened through the chooser returns to that chooser, retaining its Summary/Results context after refresh. Results-to-career links also preserve the saved Results query and its own Summary return context. The chooser reads the existing saved recommendations endpoint instead of invoking recommendation generation. Back navigation no longer waits for College-status resolution.
- Active College users have a visible **Go back to College Dashboard** button above the Assessment Summary heading, using the existing authenticated College status. The duplicate College action at the bottom is hidden for active users. Users without active tracking retain the existing Go to College Phase setup action and do not see the return button. Responsive round-trip tests at 390, 768, and 1440 px verify this visible return action, browser history/refresh, and unchanged saved recommendation/tracking fixtures.
- Abandoning Change Program, Resume, or Restart setup uses **Back to College Dashboard** and returns directly to `/college`; initial College Setup retains its ordinary Dashboard return. Entering/cancelling Change Program never submits a lifecycle mutation. The generic Dashboard status also recognizes existing tracking before the first check-in, using the existing College status lookup when legacy check-in evidence is absent. This prevents a completed assessment from routing an existing College user to Summary merely because no check-in has been completed yet.
- College Setup allows attempted continuation to trigger specific errors. Earlier/equal end dates show **The end date must be later than the start date.** Missing selections, invalid academic years/terms, out-of-year dates, incomplete approximate schedules, and invalid term positions are blocked before submission. Errors derive from current inputs, use existing FieldError/ARIA conventions, and clear when corrected. Invalid entered end dates are retained so students can understand and correct them. Backend validation is unchanged.
- Interests, Skills, and Personality reuse the existing authenticated draft endpoint and serialized save queue. Answer changes initiate saving immediately; changing only the question position does not issue a draft request. Identical consecutive saves within a page share their existing promise. Following the user's UI feedback, normal saving/success states stay silent in the background; only save failures display an accessible message and Retry action.
- Assessment step navigation and confirmed exit await pending saves. Failed saves can be retried before leaving. Requests capture their original token and attempt ID, and authentication changes invalidate queued work. Keepalive supports already-started requests across page departure; saving does not rely on unload events.
- The shared assessment header has a visible **Exit Assessment** button beside the step indicator. It opens the existing leave confirmation and uses the same pending-save guard and dashboard return flow. The logo is no longer the only exit entry point. The button remains visible on narrow screens and supports keyboard activation and restored focus after cancellation.
- The four assessment parts reuse the existing layout footer for visible **Back / Next** navigation while the content pane scrolls. Interests' former bottom-of-list controls are moved into this footer. Personal Factors requires its existing Save action before Next; Skills and Personality require their existing submission before Next advances to another part. A short footer hint explains the required action or next destination. Existing question-level controls remain separate. Duplicate continue buttons on result screens are removed; the same existing handlers run from the footer. Back awaits pending draft saves.
- The existing session record retains a pending flag/save identity, allowing refresh recovery to retry newer local answers without replacing them with an older server snapshot. A previous page's response cannot clear a newer page's pending marker.
- Missing/stale draft IDs recover from authenticated current-attempt data. Reads do not create attempts. Concurrent initial Interest recovery shares its creation request. Resume chooses the unfinished step; with no local question position it chooses the first unanswered question. College/Summary exposes Continue Assessment for an unfinished retake rather than starting another attempt.
- Leaving an unfinished assessment without College tracking stays on the main Dashboard. Its existing Continue Assessment action explicitly resumes the recovered draft. Dashboard never automatically redirects to an unfinished assessment: doing so caused Leave Assessment to loop back into the assessment. Completed-assessment and College dashboard redirects remain intact.
- Autosaved Interest selections alone do not complete Interests or advance the resume target. The existing Next submission stores server-generated `submittedAt` metadata inside the existing interests JSON; autosave strips this metadata. Dashboard and resume use the same submitted-step status. A saved selection without Next remains **1/4**, with Interests next; after Next it becomes **2/4**, with Academic Skills next. No schema change is needed. Completed assessments, legacy submitted arrays, and older attempts with downstream progress retain their completion evidence.
- Backend recovery selects only the user's latest attempt. A completed newer attempt cannot resurrect an older unfinished draft. No assessment records are deleted or reset.

Include an existing completed assessment plus College check-ins, an unfinished retake, an account with no assessments, and a mobile browser. In-app assessment exit continues to await pending saves. Personal Factors retains its existing explicit Save action, and the exit explanation calls this out.
- No WSM, assessment content/scoring, recommendation persistence/ranking algorithm, College tracking lifecycle/calculations, production data, schema, or deployment changes are included.
